    MiniMax M3 的 MSA 架构到底做了什么？一篇拆清楚「稀疏注意力」为什么能干掉全注意力

    6 月 1 日，上海稀宇科技发布 MiniMax M3，用自研的 MSA 稀疏注意力架构把 100 万 token 上下文的计算成本压到前代的 1/20，SWE-Bench Pro 跑出 59% 超越 GPT-5.5。这篇文章拆解它到底怎么做到的，以及这个成绩含金量几何。

    一个反直觉的事实：注意力越"全"，模型越笨

    标准 Transformer 的注意力机制有一个听起来很美的设定：每个 token 都看一眼所有其他 token，然后决定谁对自己最重要。

    这就像一个员工开会时必须听完所有 200 个同事的发言，才能决定跟谁对接。当会议室只有 10 个人时没问题。但当上下文窗口推到 100 万 token——相当于会议室里坐了 100 万人——这个"全部听一遍"的规则就变成了灾难。

    计算量随序列长度呈二次方增长。上下文从 4K 扩展到 1M，计算量不是增加 250 倍，而是增加 62,500 倍。

    MiniMax M3 的核心命题就是：我们不需要全注意力。我们只需要找对人。

    MSA 的核心机制：不是"看少一点"，是"精准地只看该看的"

    MSA，全称 MiniMax Sparse Attention，是 M3 自研的稀疏注意力架构。它的设计理念不是简单地砍掉一些注意力连接（很多早期稀疏方案都是这么做的，效果很差），而是动态选择最相关的 KV 块。

    用类比说：如果全注意力是"给全公司发邮件然后等所有人回复"，MSA 是"先扫一眼组织架构图，判断这件事跟谁有关，然后只问那几个人"。

    技术层面，MSA 的关键设计包括三层：

    第一层：KV Block 分区。把整个 KV Cache 切成固定大小的块（block），每个块代表一段连续的上下文片段。这不是随机切割——分区策略经过训练优化，让语义相近的 token 尽量落在同一个块里。

    第二层：块级相关性选择。对每个新的 query token，模型先用一个轻量级的评分机制扫描所有块的"摘要向量"，快速判断哪些块与当前 query 最相关，只加载得分最高的 top-K 块进行完整注意力计算。

    第三层：KV Outer Gather Q 优化。被选中的块以连续内存访问模式读取（"outer gather"），避免了稀疏访问中常见的 cache miss 问题。MiniMax 声称这个实现比 Flash-Sparse-Attention（业界常用的稀疏注意力参考实现）快 4 倍。

    整个流程可以用一张图说清楚：

    flowchart LR A["新 Query Token"] --> B["扫描所有 KV Block\n的摘要向量"] B --> C{"块级相关性\n评分排序"} C -->|Top-K 块| D["连续内存加载\n(Outer Gather)"] C -->|其余块| E["跳过 ❌"] D --> F["精细注意力计算"] F --> G["输出"]

    ▲ MSA 核心流程：不是"看少一点"，是先判断"该看谁"再精确计算

    💡
    为什么"连续内存访问"这么重要？ GPU 的显存带宽是有限的。如果注意力计算需要跳跃式读取分散在显存各处的数据，光是"找数据"的时间就可能超过"算数据"的时间。MSA 的 outer gather 设计确保被选中的 KV 块在物理上是连续排列的，让 GPU 能全速运转而不是等数据。

    性能实测：1/20 的成本不是营销话术

    MiniMax 公布的数据显示，在 100 万 token 上下文长度下：

    • 预填充（Prefill）阶段：比前代 M2 快 9 倍以上
    • 解码（Decoding）阶段：比前代 M2 快 15.6 倍
    • 每 token 计算成本：降至前代的 1/20

    这意味着什么？前代模型处理一个 100 万 token 的任务如果需要 100 美元的算力，M3 只需要 5 美元。

    值得注意的是，MiniMax 在 M2 系列中曾使用"闪电注意力"（Lightning Attention，一种线性注意力变体）。到了 M3，他们放弃了线性注意力，转向稀疏注意力。这个技术路线的"回退"本身就很有信息量——说明在实践中，精心设计的稀疏方案比粗暴的线性近似效果更好。

    Benchmark 成绩单：59% 的含金量

    M3 最抢眼的数字是 SWE-Bench Pro 59.0%。这个 benchmark 测试模型在真实开源项目中修复 bug 的能力——不是做选择题，是真的要读懂代码、定位问题、写出补丁。

    BenchmarkM3 分数对比
    SWE-Bench Pro59.0%超 GPT-5.5，逼近 Opus 4.7
    Terminal-Bench 2.166.0%CLI 任务完成率
    BrowseComp83.5超 Opus 4.7（79.3）
    MCP Atlas74.2%工具调用能力
    OmniDocBench—超 Gemini 3.1 Pro

    但这些数字需要加一个重要注脚：截至发稿，所有分数均为 MiniMax 自报，尚未有独立第三方验证。技术报告承诺在发布后 10 天内公开权重和完整评测细节。在权重公开、社区跑出独立分数之前，这些数字的可信度打个七折是合理的。

    ⚠️
    关于 Benchmark 的惯性偏差 SWE-Bench Pro 是当前编程能力评测的"黄金标准"，但它主要测试的是 Python 开源项目的 bug 修复能力。一个模型在 SWE-Bench Pro 上得分高，不代表它在所有编程任务上都领先。M3 在通用对话、创意写作等维度的表现，目前没有公开数据。

    MoE + MSA：两个"稀疏"叠加的工程哲学

    M3 的架构是 MoE（Mixture of Experts）+ MSA 的双重稀疏设计。基于前代 M2 的公开信息（总参数 2300 亿，每次推理只激活 100 亿），M3 大概率延续了这个范式。

    这两个"稀疏"解决的是不同层面的问题：

    flowchart TB subgraph M3["MiniMax M3 双重稀疏架构"] direction TB Input["输入 Token"] --> MoE_Layer subgraph MoE_Layer["MoE 层：模型稀疏"] direction LR Router["路由器"] --> E1["专家 1 ✓"] Router --> E2["专家 2 ✗"] Router --> E3["专家 3 ✓"] Router --> E4["... 专家 N ✗"] end MoE_Layer --> MSA_Layer subgraph MSA_Layer["MSA 层：注意力稀疏"] direction LR Q["Query"] --> Selector["块级选择器"] Selector --> B1["KV Block 1 ✓"] Selector --> B2["KV Block 2 ✗"] Selector --> B3["KV Block 3 ✓"] Selector --> B4["... Block M ✗"] end MSA_Layer --> Output["输出"] end

    ▲ M3 的双重稀疏：MoE 只激活部分专家（省参数），MSA 只关注部分上下文（省注意力）

    • MoE 的稀疏：解决"模型太大推理太慢"的问题。2300 亿参数的知识量，但每次只调动 100 亿参数的算力——就像一个公司有 2300 名员工，但每个项目只需要 100 人上场。
    • MSA 的稀疏：解决"上下文太长注意力太贵"的问题。100 万 token 的记忆容量，但每次只关注最相关的那些片段。

    两层稀疏叠加的结果：M3 的 API 定价是输入 $0.60/百万 token、输出 $2.40/百万 token（促销期半价）。对比 Claude Opus 的 $5/$25 和 GPT-5.5 的约 $10/$30，M3 的成本只有顶级闭源模型的 5%–10%。

    这不是因为 MiniMax 在做慈善，而是因为双重稀疏架构确实把推理成本压到了极低水位。对开发者来说，这意味着AI Agent 的部署成本计算可能需要重新来过。

    12 小时复现 ICLR 顶会论文——这个能力意味着什么

    MiniMax 展示了一个极端测试场景：让 M3 在无人工干预的情况下，12 小时内自主复现了一篇 ICLR 顶会论文的完整实验。

    更惊人的是第二个测试：M3 连续运行 24 小时，调用工具近 2000 次，将 Hopper 架构上 FP8 矩阵乘法的硬件利用率从 7.6% 提升至 71.3%——一个经验丰富的 CUDA 工程师可能需要一周完成的优化任务。

    这展示的不是"模型很聪明"，而是长线程自主规划能力——在超长上下文中保持连贯的目标追踪、错误恢复和迭代优化。这正是 MSA 架构带来的直接红利：因为 100 万 token 上下文的计算成本可控，模型才能在长时间任务中保持完整的工作记忆。

    这种能力对AI Agent 的自主工作架构有深远影响——Agent 的"记忆力"不再是架构瓶颈，而是一个可以用算力换取的资源。

    与同行的本质差异：MSA vs MLA vs 全注意力

    当前大模型在注意力机制上有三条主要技术路线：

    方案代表核心思路代价
    全注意力GPT-5.5、Claude Opus每个 token 看所有 token计算成本 O(n²)，长上下文极贵
    MLA（多头潜注意力）DeepSeek V3/V4压缩 KV Cache 表示精度可能有损，实现复杂
    MSA（稀疏注意力）MiniMax M3动态选择相关 KV 块选择机制可能漏掉重要信息

    DeepSeek 的 MLA 走的是"压缩"路线——把 KV Cache 投影到更低维的潜空间，减少存储和计算。MiniMax 的 MSA 走的是"选择"路线——不压缩，但只读取最相关的部分。

    两种路线各有取舍。MLA 的风险是压缩带来的信息丢失（尤其在需要精确回忆细节的任务中）；MSA 的风险是选择机制可能"看走眼"——遗漏了看起来不相关但实际重要的上下文。

    从 benchmark 结果看，MSA 在编程和工具调用类任务上表现出色（这类任务的相关性比较明确，"该看谁"比较好判断）。但在需要全局信息整合的任务（如长文档摘要、复杂推理链）中，MSA 是否仍然占优，目前缺乏公开数据。

    冷静判断：M3 的真实定位

    我的判断是：M3 是当前开源/开权重模型中最强的编程和 Agent 类模型，但不是全能冠军。

    支撑这个判断的几个事实：

    1. 它确实在特定维度超越了闭源顶流。即使 SWE-Bench Pro 的数字打七折（42%），仍然是开源模型中的最高水平。BrowseComp 超越 Opus 4.7 这个数据如果属实，说明在工具调用和自主浏览场景下 M3 是实打实的第一梯队。
    2. 但通用能力的位置不明。没有公布 MMLU-Pro、GPQA、创意写作等通用 benchmark。一个专攻编程的模型在通用能力上通常不会同时登顶。
    3. 开源承诺尚未兑现。权重和技术报告承诺 10 天内发布，但截至本文发稿（6 月 2 日），尚未看到 HuggingFace 或 GitHub 上的正式发布。
    4. 定价极具竞争力。如果性能数据属实，M3 提供了一个"闭源模型 5% 的价格，80%+ 的编程能力"的选项，这对生产环境部署 AI Agent 的成本结构是颠覆性的。

    对于开发者来说，值得关注但不急于 all-in。等权重公开、社区跑出独立 benchmark 之后，再做技术选型也不迟。

    对于行业观察者来说，M3 传递的更大信号是：中国开源大模型已经从"追赶闭源"进入"在特定维度超越闭源"的阶段。从 Qwen3 到 DeepSeek V4 再到 MiniMax M3，这已经不是一两个异常值，而是一个趋势。
