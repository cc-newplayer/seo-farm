MCP 凭什么在六个月内装机 9700 万次
——AI 协议战争的胜负手

一个给 AI 模型用的连接协议，为什么能跑出 npm 热门框架六年才有的下载密度？本文从架构设计、生态博弈和竞争对比三个维度，还原 MCP 赢得这场协议战争的完整逻辑。

2026 年 3 月，Anthropic 公布了一个数字：MCP 的安装量突破 9700 万次。

这个数字意味着什么？作为对比，npm 上最热门的 JavaScript 框架 Express.js 花了六年才达到类似的下载密度。MCP 用了不到六个月。

为什么一个「给 AI 模型用的连接协议」能跑出这样的速度？这背后不是营销胜利，而是一场关于架构设计、时机判断和生态博弈的系统性胜利。

一、问题的起点：AI 模型本质上是个「封闭系统」

在 MCP 出现之前，AI 模型的工作方式类似一位博学但闭关的专家——他知识丰富，但只能靠你递进去的信息来回答问题。

想让 Claude 帮你查最新的 GitHub Issue？你得手动复制粘贴。想让 GPT 帮你查公司数据库？你得先把数据导出，再贴给它。想让任何模型使用任何工具？每家公司都要自己写一套对接代码，互不兼容。

这个问题在 2024 年之前一直以一种临时修补的方式存在：Function Calling。OpenAI 最先推出，各家跟进，开发者们写 JSON Schema 描述工具，让模型学会调用。

但 Function Calling 有一个根本缺陷：它只解决了「模型怎么调用工具」的问题，没有解决「工具怎么被任何模型发现和使用」的问题。

每一对（模型 × 工具）都需要单独集成。1000 个工具 × 10 个模型 = 10,000 个集成点。这是一个在规模上不可持续的架构。

二、MCP 的核心设计：把「N×M」变成「N+M」

计算机科学里有一个经典的解题思路：当你面对 N×M 的复杂度问题时，引入一个中间抽象层，把它变成 N+M。

这正是 MCP（Model Context Protocol，模型上下文协议）的核心贡献。

MCP 定义的不是一个功能，而是一套协议标准。它规定了：

  • AI 模型（Host）怎么声明自己需要什么能力
  • 工具提供方（Server）怎么暴露自己的功能
  • 两者之间用什么格式交换数据
ℹ️
类比理解 MCP 就是 USB-C。在 USB-C 之前，你需要为每种设备准备专属充电线；USB-C 之后，一根线连所有设备。MCP 做的是同样的事——任何实现了 MCP 的 AI 模型，可以直接使用任何实现了 MCP 的工具，中间不需要额外的「翻译层」。

从开发者的视角，这意味着：写一次 MCP Server，所有兼容 MCP 的模型都能用；把模型接入 MCP，所有兼容 MCP 的工具都可以调用。N 个模型 + M 个工具 = N+M 个集成点，而不是 N×M。

三、为什么是 Anthropic 来做这件事

这里有一个值得思考的问题：MCP 这样的协议标准，OpenAI 为什么没有先做？

答案可能反直觉：市场领导者通常没有动力推动开放标准，因为开放标准会削弱自己的护城河。

OpenAI 在 2024 年拥有最大的模型市场份额。封闭生态对它有利——开发者习惯了 OpenAI 的 Function Calling 格式，换模型的迁移成本就越高，留存率就越高。

Anthropic 的处境不同。2024 年的 Anthropic 是一个高质量但市场份额相对较小的竞争者。对它而言，推动开放标准是有利的：如果 MCP 成为行业规范，Claude 作为「天然兼容 MCP」的模型，会在所有 MCP 工具生态中获得自动曝光，弥补渠道劣势。

这不是慈善，这是策略。

2024 年 11 月，Anthropic 发布 MCP 并宣布开源，同时发布了 Python 和 TypeScript SDK、参考实现和文档。这个「开放赠送」的动作，本质上是在快速建立生态门槛——等其他公司意识到并跟进时，MCP 生态已经有了先发优势。

四、MCP vs Function Calling vs REST：协议层的本质差异

有必要厘清 MCP 与其他集成方案的本质区别，因为这常常是理解误区的来源。

维度 Function Calling REST API MCP
设计目标 让模型学会调用工具 系统间数据交换 AI 模型与工具的标准化互联
发现机制 无（需手动注册每个工具） 无标准（靠文档） 有（Server 自动声明可用工具）
上下文传递 依赖模型的 context window 无状态 有状态，支持多轮会话
跨模型兼容 各家格式不同，不兼容 可以，但需要额外适配 原生兼容，写一次到处用
安全模型 依赖调用方实现 OAuth、API Key 等 内置权限声明，Host 控制授权

最关键的差异在发现机制。REST API 需要你提前知道有哪些 endpoint；MCP Server 会在连接时主动告诉 Host「我能做这些事」。这使得动态工具组合成为可能——Agent 可以在运行时决定调用哪个工具，而不需要在设计时把所有工具都硬编码进去。

值得注意的是，MCP 本质上是在 JSON-RPC 2.0 协议上的扩展，不是完全另起炉灶。这降低了实现门槛，是它能快速普及的技术原因之一。

五、9700 万次安装的背后：生态雪球是怎么滚起来的

协议标准靠「好设计」起步，靠「生态网络效应」胜出。MCP 的生态滚动过程有清晰的时间线：

  • 2024 年 11 月：Anthropic 发布 MCP，Claude Desktop 原生支持，同时开源参考实现。初期用户主要是开发者和重度 Claude 用户。
  • 2025 年 Q1：GitHub Copilot、Cursor、Windsurf 相继宣布支持 MCP。关键转折点——当代码编辑器开始支持，潜在用户从「Claude 用户」扩展到「所有使用 AI 编程工具的开发者」。
  • 2025 年 Q2-Q3：Notion、Linear、Sentry、GitHub、Slack 等主流开发者工具相继发布官方 MCP Server，工具多了→模型用 MCP 的理由更强→更多模型支持 MCP→工具开发 ROI 更高，正向飞轮形成。
  • 2025 年底：微软将 MCP 集成进 VS Code，Google 在 Gemini 中支持 MCP，从「Anthropic 的开源项目」变成「行业标准」。
  • 2026 年 3 月：安装量 9700 万，中国工业和信息化部将 MCP 安全规范纳入立项，成为首个被纳入官方监管框架的 AI 协议。
ℹ️
里程碑 截至 2026 年 3 月，MCP 已成为每个主要 AI 提供商都支持的工具集成标准，包括 Anthropic、OpenAI、Google、Microsoft 和 Meta。

六、MCP 的局限性：它没有解决的问题

任何技术都有边界，MCP 也不例外。

认证和安全是当前最大的挑战。MCP 规范定义了权限声明机制，但没有规定具体的认证实现。这意味着不同的 MCP Server 实现质量参差不齐，安全审计难度大。2025 年已有多起「工具中毒」（Tool Poisoning）攻击案例。

⚠️
安全提示 只从可信来源安装 MCP Server。恶意 MCP Server 可以通过「工具描述」操控 AI 模型的行为，这类攻击已有真实案例记录。

性能开销不可忽视。MCP 的状态管理和工具发现机制引入了额外的通信开销，对延迟敏感场景（如实时对话）需要仔细评估。

版本兼容性仍在演化。2025 年 11 月的规范与初版有较大差异，依赖旧版实现的 Server 可能在新版 Host 上出现兼容问题。

我认为，MCP 最大的风险不是技术缺陷，而是碎片化。随着越来越多的公司推出「MCP 兼容」的产品，规范解释分歧和私有扩展可能导致实际上的兼容性问题。2026 MCP 路线图中的「治理成熟度」目标，正是在解决这个问题。

结论：MCP 赢了协议战争，但这只是第一局

MCP 能在六个月内达到 9700 万安装量，原因是三件事同时成立：

  1. 解决了真实的架构痛点（N×M → N+M）
  2. 时机恰好（AI Agent 爆发期，工具集成需求急剧增长）
  3. 推动者的激励结构正确（Anthropic 作为市场追赶者，推开放标准符合其利益）

真正的挑战是：当 MCP 生态足够大时，它能否保持治理质量，避免「标准」变成「名义上的标准」？这是 2026 年 MCP 社区要解答的核心问题。
